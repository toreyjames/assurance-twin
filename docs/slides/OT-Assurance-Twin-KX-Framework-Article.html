OT Assurance Twin: A Context-Aware Framework for OT Asset Assurance

Subtitle: A client-customizable framework—not a fixed tool—for building verified, context-aware OT asset canons with engineering-backed intelligence.
Industry Focus: Oil & Gas, Pharmaceuticals, Automotive, Utilities

Executive Summary

Operational Technology (OT) environments face a critical visibility gap: organizations typically have only 50–80% visibility into their OT assets, creating blind spots that compromise security, compliance, and operational efficiency. Traditional approaches—OT security platforms, CMDB systems, and engineering documentation—operate in silos, providing fragmented views that lack context and verification.

The OT Assurance Twin is presented here as a framework—a set of principles and building blocks that are customized per client—rather than as a single tool. Implementation is tailored to client data sources, industry, unit taxonomy, and assurance depth (inventory, context, or full assurance); the principles remain consistent. The framework fuses multiple data sources (engineering baseline, OT discovery, CMMS, and related feeds) into a single, verified, context-aware asset canon with process-aware intelligence, grounded in the AIGNE academic framework and semantic mapping functions for context awareness.

This article describes the framework’s foundation (AIGNE), its semantic and mapping functions, its context-aware analysis capabilities, and the careful role it plays in risk: providing engineering-backed context that is often the missing piece to risk assessment and prioritization—enabling CISOs to see risk through an OT lens and to explain and justify prioritization and timing with evidence.

What This Is—and What This Is Not

This Is:

  • A Framework—reusable design and building blocks, configurable to client data sources, industry, unit taxonomy, and assurance depth
  • A Reference Model for context-aware OT asset assurance—design principles that guide implementation
  • A Design Pattern that prioritizes process intent and engineering context over raw lists
  • Client-Customizable—implementation is customized per engagement; the principles are consistent
  • Aligned with Risk Relationships—prioritizing client protection and auditability over feature proliferation

This Is Not:

  • Not a Fixed Tool—we describe a framework and approach, not a single shrink-wrapped product
  • Not a Platform Pitch—no vendor lock-in; the framework can be applied with client-chosen data and systems
  • Not One-Size-Fits-All—every plant and client is different; the framework adapts to context
  • Not a Replacement for Risk Judgment—we provide context that enables risk-informed decisions; we do not “calculate” or “determine” risk in a definitive way

The distinction matters. The framework starts from the problem: how do we build a verified, context-aware view of OT assets so that security, operations, and compliance can make informed decisions? The answer is not “deploy our product”—it’s “apply this framework and customize it to the client.”

Foundation: AIGNE

The framework is grounded in the AIGNE academic framework (arXiv:2512.05470), which provides principles for context-aware engineering, traceability, and accountability. Three AIGNE-aligned ideas are central:

  • Context Constructor—context is “assembled under explicit architectural design constraints.” In practice: multi-source ingestion (engineering, discovery, and other feeds), normalization to a canonical schema, and multi-strategy matching (e.g. tag ID, IP, hostname, MAC) with confidence tiers. The result is a single asset canon with clear lineage.
  • Provenance and accountability—“context artefacts must be traceable and accountable.” Every source ingestion, match, and pipeline step is recorded. Match strategy and confidence are stored so that auditors and regulators can answer “how do we know?” with evidence.
  • Agentic File System (AFS)—all context sources are treated as “files” in a governed, persistent, hierarchical file system. Sources, canonical outputs, and derived artefacts have identity and lineage; derivation relationships (e.g. “this canon was derived from these source files”) support full traceability.

Together, these ensure that the framework does not just produce another list: it produces a verified list with a clear audit trail and the ability to trace any assertion back to source data and matching logic.

Conceptual flow: Client data sources (engineering baseline, OT discovery, CMMS, etc.) → Agentic File System & Context Constructor → Provenance-tracked canonical context → Semantic mapping & context-aware analysis → Canon, reports, and visual outputs.

Framework layers: ingestion and construction (AIGNE-aligned), then semantic mapping, then analysis.

Semantic and Mapping Functions for Context Awareness

Context-aware assurance requires understanding not only what assets exist but what they do, where they sit in the process, and what is expected for each unit. The framework uses semantic and mapping functions to provide that context.

Device semantics

Device semantics are derived from tag naming conventions and device types. Industry-standard patterns (e.g. ISA-5.1) are used: the first letter of a tag often indicates the measured variable (e.g. F = flow, L = level, T = temperature), and modifier letters indicate function (e.g. transmitter, controller, valve). From tag and model information, the framework infers device type (PLC, SIS, transmitter, HMI, etc.) and criticality. This enables “what this device is and what it does” rather than a bare identifier.

Unit knowledge

Industry-specific templates define what each process unit is expected to contain: expected functions (e.g. feed flow control, column pressure, safety systems) and expected device types (e.g. minimum PLCs, SIS, HMIs per unit). This enables functional gap analysis—not just “we have or don’t have this asset” but “this unit is missing an expected function or device type.” Templates can be customized per client and industry (oil & gas, pharma, automotive, utilities).

Dependency mapping

Dependencies between units and assets are modeled (process flow, control, safety, utility, network). Industry-specific patterns describe typical process flow (e.g. crude distillation → hydrotreater) and utility consumption (e.g. steam, instrument air). This answers “what else fails when this fails?” and supports prioritization and impact analysis.

Industry auto-detection

In line with AIGNE’s principle to “detect and adapt to data patterns rather than requiring upfront configuration,” the framework can infer likely industry from ingested data—unit names, equipment types, and terminology—so that semantic and mapping functions can be applied with minimal manual configuration.

Context-Aware Analysis (Beyond a Simple List)

With semantic and mapping functions in place, the framework supports analysis that goes beyond a flat inventory.

  • Gap analysis—Asset gaps (blind spots: in engineering but not discovered; orphans: discovered but not in engineering), functional gaps (missing expected functions or device types per unit), and coverage gaps (units or segments with insufficient discovery visibility). All use device context and unit knowledge.
  • Lifecycle context—EOL/EOS data, firmware age, and support status answer “how long do we have?” and inform prioritization.
  • Layout and ISA-95—Deterministic, engineer-grade layout and ISA-95/Purdue zone awareness support both data semantics and visual representation (e.g. plant maps with zone boundaries and process flow), so the same context appears in reports and in visualizations.

The emphasis throughout is context over lists: the framework produces a canon that is not only matched and verified but also interpreted—what it does, where it sits, what’s missing, and how it fits the process.

Risk: Context as the Missing Piece

In OT, risk cannot be properly qualified without engineering context. A list of devices with IP addresses and CVEs does not tell the CISO which devices sit in safety-critical loops, which units cannot be taken offline without process impact, or why an engineer might say “patch later, not now.” The framework is designed to supply that missing piece: engineering-backed context that enables risk-informed decisions, without replacing risk judgment.

CISO lens, engineering data primary

The primary audience for risk-related outcomes is the CISO (and board/audit). In OT, however, engineering data is primary to qualify risk. The framework delivers a CISO-relevant view—what needs attention, where gaps are, what is managed—grounded in engineering baseline and discovery, so the CISO can speak with evidence rather than assumptions.

A familiar tension: for a CISO, “everything needs to be patched”; an engineer may say “yes, but not now.” The framework helps explain and understand why “not now”—process criticality, unit role, safety function, outage windows, and dependencies. It gives the CISO the language and evidence to align with operations and to justify prioritization and timing to auditors and leadership. We do not claim to “calculate” or “determine” risk in a definitive way; we provide context that enables risk-informed decisions and qualifying risk with engineering data.

From Framework to Application

The framework is applied in engagements by configuring it to the client: data sources (engineering spreadsheets, discovery exports, CMMS, vulnerability data), industry (and thus unit and dependency templates), and assurance tier (inventory-only, context-rich, or full assurance with gap and compliance-oriented outputs). Visual and report outputs—plant maps, gap matrices, executive summaries, evidence packages—are outcomes of the same semantics and provenance, so that what appears in a dashboard or report is traceable to the same canon and rules.

Because it is a framework and not a fixed product, deliverables can be tailored: some clients need a verified asset list with provenance; others need functional gap analysis by unit; others need engineering-backed context for risk prioritization and “why not now” discussions. The building blocks (Context Constructor, provenance, AFS, semantic and mapping functions, context-aware analysis) remain the same; the implementation is customized.
